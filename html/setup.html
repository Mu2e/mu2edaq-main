Common setup

Everything below assumes the mu2edaq-main superproject layout — one checkout containing every application as a git submodule, at ~/mu2edaq-main on the DAQ hosts.

1 · Get the code

$ git clone --recurse-submodules git@github.com:Mu2e/mu2edaq-main.git
$ cd mu2edaq-main
# already cloned without submodules?
$ git submodule update --init --recursive

2 · Platform baseline

The production platform is AlmaLinux 9 with the system Python 3.9; every package in the suite is verified against it (macOS also works for development). GUI apps need a display — inside the control room that is the app's assigned VNC session.

3 · The bootstrap pattern

Every Python application keeps its own virtual environment in ./venv, created by the package's bootstrap script (bootstrap*.sh). Bootstrap once per checkout, re-run after dependency changes:

$ cd mu2edaq-<app>
$ ./bootstrap*.sh
Four packages (downtime-logger, dataformat-viewer, heartbeatmonitor, resource-manager) also depend on mu2edaq-discovery, which is not on PyPI — install the sibling checkout into their venv first: venv/bin/pip install ../mu2edaq-discovery (mu2edaq-main#4).

4 · The crs-app launcher and ports

Desktop icons and shift procedures start applications with crs-app start <id> (from mu2edaq-controlroom-setup). The launcher reads config/apps.yaml, exports CRS_PORT_<NAME> for each of the app's ports, and execs the app's standardized start script. Started by hand, the same scripts fall back to identical built-in defaults — see the port map.

5 · Verify the whole suite

The superproject ships a compatibility harness that builds and smoke-tests every package:

$ ./mu2edaq-build-all.sh            # venvs, editable installs, CMake builds
$ ./mu2edaq-test-all.sh             # imports, CLI smokes, pytest, ctest -> .compat/report.md
$ source mu2edaq-setup-env.sh <pkg> # work inside one package's environment
